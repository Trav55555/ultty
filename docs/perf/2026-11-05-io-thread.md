# PTY Throughput After the I/O Thread (2026-11-05)

Measurements behind the `vt-core-fixes` branch: graphemes on rows, VT core
fixes, the per-terminal PTY I/O thread, and the grid buffer pool.

## Setup

- Machine: AMD Ryzen 5 7600, Linux 7.0, Wayland, release builds.
- Payload: 64 MiB of `the quick brown fox ... \033[1;32mgreen\033[0m` lines.
- Live: launch `ultty`, open a tab with `ulttyctl new-tab`, `cat` the file
  three times, time each `cat` inside the shell. Builds were alternated
  run by run; nothing else heavy was running.
- Headless: `cargo run --release -p ultty-vt --example throughput -- <file>`
  (parser and grid only) and
  `cargo run --release -p ultty --example pty_throughput -- <file>`
  (real PTY plus I/O thread, no renderer).

## Results

| Measurement | Before | After |
|-------------|--------|-------|
| Headless parse + grid, mixed SGR text | 118 MiB/s | 138 MiB/s |
| Headless parse + grid, 62-byte lines | 110 MiB/s | 124 MiB/s |
| Headless parse + grid, 4000-char wrapped lines | 215 MiB/s | 286 MiB/s |
| Headless PTY + I/O thread, no renderer | n/a | 123-127 MiB/s |
| Live, 800x600 window | 114-125 MiB/s | 110-127 MiB/s |
| Live, 2560x1400 window | 63-89 MiB/s | 78-87 MiB/s |
| `render_filled/terminal/200x60` | 1.36 ms | 1.29 ms |

## Reading the numbers

- The [2026-05-14 live stress](2026-05-14-live-stress.md) figure of 14 MiB/s
  does not describe current code; on this machine the single-threaded build
  already reached ~120 MiB/s, bound by parse and grid work, not by frame
  pacing.
- Live throughput now equals the headless PTY figure: drawing costs nothing
  extra at normal sizes, and the limit is the VT core plus kernel PTY
  delivery.
- At large window sizes the renderer builds vertices while holding the
  terminal lock, which costs about a third of throughput. Backlog item 6
  (render from a snapshot) addresses it.
- Without wake throttling, the I/O thread made the large-window case 3x
  slower (29 MiB/s): the UI woke for every chunk and contended for the lock.
  Output wakes are now limited to one per 4 ms with a trailing wake.
- What the I/O thread changes is where parsing happens: the UI thread no
  longer drains up to 1 MiB of output before it handles a key press. No
  input-latency number was measured for this report.
