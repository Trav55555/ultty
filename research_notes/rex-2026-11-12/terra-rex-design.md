# Rex design research

Research date: 2026-11-12. Sources are Superlogical's public documentation, which describes a moving beta and multiple release channels. This is a published-contract analysis, not inspection or reproduction of Rex's implementation. The supplied video is being handled separately. No benchmark was run.

## Assessment for Ultty

Rex's strongest relevant design is its server-owned session model and its separate, discoverable control and block-data interfaces. It makes sessions, layouts, terminals and actions addressable by both humans and automation. Its snapshot-plus-events attach contract gives a concrete answer to the race between initial state and subsequent changes. The highest-value Ultty exploration is a small local control interface with explicit session identities, attach/reconnect and bounded backpressure, preserving Ultty's existing VT and native region protocols. A network listener, multi-user service, Lua runtime and plugin architecture each introduce substantial additional security and compatibility work and should be separately justified.

This is an architectural comparison, not a claim that Rex's data protocol or internal representation matches Ultty's. Rex's docs do not establish its grid representation, parser, rendering pipeline, disk format, complete wire specification, or performance relative to Ultty. An OSC 7501 compatibility prototype is a much smaller independent experiment than adopting the whole server architecture.

## Model and persistence

- Rex exposes sessions, windows, layouts and blocks; a detached block keeps running. [CLI reference](https://www.superlogical.com/rex/docs/reference/cli).
- Local personal, shared and login-server modes have distinct OS authority. A shared server runs all programs as the `rex` account and shared group members can see and type in all sessions. A root login server maps connection identities to permitted OS accounts and proxies to a per-account server. [Server modes](https://www.superlogical.com/rex/docs/linux/server-modes), [login server](https://www.superlogical.com/rex/docs/linux/login-server).
- Client/network disconnect is distinct from server shutdown: turning off Tailscale closes those connections while sessions continue. Server stop ends every program in sessions; package upgrades restart the service and end sessions. A server has a state directory and `--restore` defaults to true, but those facts do not imply process checkpointing or preservation of live children across a server restart. The public CLI description does not specify which parts of terminal history or process state are restored. [CLI reference](https://www.superlogical.com/rex/docs/reference/cli), [server modes](https://www.superlogical.com/rex/docs/linux/server-modes).
- CLI capture supports text, HTML and VT; documented scrollback is approximately 64 MiB per terminal, with old lines dropped at the limit. Line count depends on width and styling. This is a configured product limit, not evidence of throughput or disk persistence. [CLI reference](https://www.superlogical.com/rex/docs/reference/cli).

## Replication and concurrency contract

- `session.attach` subscribes before reading its view; apply the view then events with higher sequence numbers. `session.attach_all` has an analogous snapshot rule, with gapless ordered events and an 8 MiB lag limit followed by disconnect. Do not assume this guarantee applies to every data channel. [Server API methods](https://www.superlogical.com/rex/docs/reference/api).
- `session.view` has a per-session revision. View-change notifications can arrive out of revision order and carry a revision rather than the full view; fetch the view on a higher revision and retain the highest. These are control-plane snapshots and invalidations, not proof of a particular cell-diff replication algorithm. [Server API methods](https://www.superlogical.com/rex/docs/reference/api).
- `data.connect` issues a one-use, expiring ticket for a block data WebSocket. The ticket can bind a subprotocol such as `rex.data.terminal.v1`. This establishes separate control and streaming channels, not complete framing or recovery semantics. [Server API methods](https://www.superlogical.com/rex/docs/reference/api).
- Keys and layout/focus operations are ordered per connection, but block methods may run concurrently; await dependencies. [Server API methods](https://www.superlogical.com/rex/docs/reference/api).

## Transport and trust

- Linux and FreeBSD default to local Unix sockets. The Mac app starts its local server without network listeners or Tailscale. Remote options include SSH forwarding, embedded Tailscale, Tailscale Serve or tailnet listeners, and explicitly enabled anonymous HTTP over a trusted network/VPN. [Remote access](https://www.superlogical.com/rex/docs/linux/remote-access), [privacy](https://www.superlogical.com/rex/docs/reference/privacy).
- Current Rex trusts connection-derived identity. Full authentication/authorization including existing SSH keys is planned, not a currently documented native capability. Plain HTTP requires `--allow-anonymous`; reachable callers have full server access, including starting programs as the server account. Tailscale identifies callers and can apply network ACLs; its access policies and account mapping remain material. [Remote access](https://www.superlogical.com/rex/docs/linux/remote-access), [login server](https://www.superlogical.com/rex/docs/linux/login-server).
- Embedded Tailscale acts as its own device and needs MagicDNS and HTTPS certificates. Pairing QR contains an address, not credentials; clients still need tailnet access. By default the server and CLI make no outbound connections. Enabling embedded Tailscale changes that and entails Tailscale coordination/relay and related network traffic. [Remote access](https://www.superlogical.com/rex/docs/linux/remote-access), [CLI reference](https://www.superlogical.com/rex/docs/reference/cli), [privacy](https://www.superlogical.com/rex/docs/reference/privacy).
- This trust model is unsuitable as a template for an unrestricted public HTTP endpoint. For Ultty, establish local peer authorization and scope of read, input, process creation, and client action permissions before proposing remote transport. A data ticket alone does not authenticate the initial control connection.

## Automation and protocols

- The server advertises methods, input/output schemas, examples and block types through `help.all`, `GET /api/help`, and `/llms.txt`; CLI supports `rex api list` and `rex api describe`. Capabilities reflect the connected server rather than a fixed client copy. This discoverability is practical for CLI tooling and agents, though schema presence does not prove compatibility or security. [Server API](https://www.superlogical.com/rex/docs/automate/server-api), [API methods](https://www.superlogical.com/rex/docs/reference/api).
- Lua 5.1 config and `rex do` scripts can call the API; CLI scripts run locally with the Lua standard library including `io`, `os` and `require`, except `io.popen` and `os.execute`; command execution uses `rex.exec`. Scripts may subscribe to events and act across configured hosts. Treat a script as trusted code, not sandboxed automation. [Lua scripts](https://www.superlogical.com/rex/docs/automate/lua-scripts), [Lua API](https://www.superlogical.com/rex/docs/reference/lua).
- Server flags document executable block-plugin discovery and reload; the documentation navigation labels Block Plugins without a linked public guide. Do not infer stability, isolation, published SDK, or third-party compatibility from these flags. [CLI reference](https://www.superlogical.com/rex/docs/reference/cli), [documentation index](https://www.superlogical.com/rex/docs/installation).
- OSC 7501 is a public program-status proposal with `idle`, `working`, `done`, `blocked`, `error` and `clear`, hierarchical records and optional feature detection. Rex documents current session/tab indicators and Lua events; push notifications and a unified priority inbox are future plans. It treats report text as untrusted and specifies bounds, control-character rejection and rate limiting for effects outside the terminal. An Ultty prototype could implement parsing, bounded records, reset/lifetime semantics and feature detection, then test real OSC input and malformed/oversized cases without committing to remote access. The spec is a vendor-authored proposal; broad ecosystem adoption and OSC-number collision status were not established. [Program Status Protocol](https://www.superlogical.com/rex/docs/build/program-status).

## Availability, evidence limits, and next checks

The public installation page says macOS app and Linux/FreeBSD servers are available to beta testers; Windows server access is restricted to testers with the Windows role. It describes iOS, Linux and Windows clients as being at varying readiness and not yet part of testing. iOS reference pages are not evidence of general availability. Individual API entries tagged Snapshot are newer than preview, so availability should be checked against the actual server's discovery output. [Installation](https://www.superlogical.com/rex/docs/installation), [API methods](https://www.superlogical.com/rex/docs/reference/api).

No comparable official reproducible benchmarks were located in this research. In particular, documentation of smooth client-side resize preview does not establish latency, throughput, CPU, memory, bandwidth or fidelity against Ultty. [Mac settings](https://www.superlogical.com/rex/docs/reference/mac-settings). Test any future claims with versioned binaries, workloads, machine, PTY output rates, local and remote latency, screen fidelity, reconnect, slow consumer, and resource measurements.

Unknowns requiring hands-on evidence or fuller primary documentation: terminal stream framing and compression, exact snapshot contents and replay after data-stream loss, which state survives crash/restart, atomicity of persisted state, multi-client size/focus arbitration, plugin process isolation, auth rollout, protocol version guarantees, and supported platform/release-channel differences. Do not equate saved session restoration with checkpoint/restore of a process. Do not infer Rex internals from an independent clone.


## Architecture: bytes, state and composition

In his July 2026 [architecture discussion](https://x.com/mitchellh/status/2082936029426892960), Mitchell Hashimoto confirmed that the server parses terminal output too, while output is teed ahead of the server's parser so clients and server can parse concurrently, with queues for slow participants. He contrasted client-owned state with transporting screen diffs. His same discussion described WebSockets over HTTP as the then-current transport, explicitly subject to change. The original X page returned HTTP 403 during this research; his replies were read in a [third-party reproduction of the discussion](https://xitter.cf/mitchellh/status/2082936029426892960), not from a directly accessible primary endpoint. Treat this as an attributed historical design statement until the original video or current wire contract is independently checked. It does not establish whether every frame is raw PTY data, current snapshot encoding, or that parsing occurs only on clients.

The documented window layout consists of split and block nodes, with atomic creation of a new layout. Windows and blocks are controlled as structured entities; this differs at the interface from forwarding a single pre-composited terminal image. That observation does not establish Rex's GPU compositing internals, nor prove performance superiority. [Server API methods](https://www.superlogical.com/rex/docs/reference/api), [Mac actions](https://www.superlogical.com/rex/docs/reference/mac-actions).

## Workflow and multi-client behavior

- The Mac action catalog lists directional splits and focus, best-fit split, pane movement, floating panes, zoom, tab tear-off and a session switcher. It assigns `Cmd+D` to split right and `Cmd+K` to switch sessions. The CLI's zoom changes presentation without changing the underlying layout. These are documented features of the client/actions, not a claim of exact feature parity across platforms. [Mac actions](https://www.superlogical.com/rex/docs/reference/mac-actions), [CLI reference](https://www.superlogical.com/rex/docs/reference/cli).
- Lua-defined custom actions can be exposed via command palette or shortcut. Config supports prefix sequences and named key modes; a resize mode can bind arrows until exited. Config is server-read and manually reloaded, with connected clients notified. A Lua syntax error preserves the previous successful configuration, while invalid individual calls can be skipped with diagnostics. [Configuration](https://www.superlogical.com/rex/docs/customize/config), [key sequences](https://www.superlogical.com/rex/docs/customize/key-sequences), [key modes](https://www.superlogical.com/rex/docs/customize/key-modes).
- A block follows its owner on conflicting sizes. Clients may take or request ownership, which confers no other rights. This is size arbitration, not an exclusive-input lock. [Server API methods](https://www.superlogical.com/rex/docs/reference/api).
- The event API exposes server, session and terminal events, including child exit and working-directory changes, to Lua or the CLI stream. That supports automation driven by semantic events rather than repeated screen scraping, subject to each event's actual documented semantics. [Events](https://www.superlogical.com/rex/docs/reference/events).

The supplied video's server-stop example uses a custom agent-resume mechanism, as established by the separately captured transcript. It cannot substantiate a general promise that arbitrary processes survive server shutdown. The video's open-source and extensible-block statements should be treated as forward-looking rather than confirmed delivery.
