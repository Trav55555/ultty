# Tailscale integration: independent review

Research date: 2026-11-12. This assessment uses current public Tailscale documentation and the official Rust repository. It is a design recommendation, not a running integration or benchmark. Ultty's documented native protocol already works in-band through SSH; the question is whether Tailscale adds enough user value to justify owning another network integration.

## Recommendation

Keep networking disabled by default. Prefer user-managed Tailscale and ordinary SSH to a remote host for a first supported workflow, using Ultty's existing in-band transport. This leaves enrollment, node identity, authentication, and network lifecycle with the user's existing tools. Validate that exact workflow before designing an embedded node. Tailscale provides connectivity, not reconnectable terminal sessions: continued jobs need a separately managed persistent session owner on the remote machine. Ultty's guide describes in-band SSH support; it does not establish such a server. [Ultty architecture](../../CLAUDE.md), [SSH over Tailscale](https://tailscale.com/docs/reference/ssh-over-tailscale).

This recommendation does not require native Tailscale SSH. Ordinary OpenSSH over the tailnet retains SSH key and server policy semantics; Tailscale SSH is a distinct opt-in server with its own SSH policy and identity model. A separate embedding decision should have a demonstrated user need, threat model, supportable dependency closure, and user-controlled lifecycle. It should not be bundled into generic remoting or enabled automatically.

## Rust library and Go tsnet

The official [tailscale-rs repository](https://github.com/tailscale/tailscale-rs) currently presents the library as pre-1.0 work in progress without compatibility guarantees. Its current main README shows the 0.7 dependency line, supported Rust MSRV 1.97 and edition 2024. The [manifest](https://github.com/tailscale/tailscale-rs/blob/main/Cargo.toml) separately declares a hard compile floor of 1.92.0. Both exceed Ultty's declared MSRV of 1.90. That is a direct current workspace policy conflict, not a reason to silently bump the toolchain. Direct connections work in many cases but NAT traversal remains in progress, with extra DERP fallback possible. Peer relays, MagicDNS, HTTPS certificates, Tailscale Serve and the full Tailscale SSH feature appear in the unsupported list. Verify the exact chosen release and source revision before a new assessment.

The official [0.6.0 changelog](https://github.com/tailscale/tailscale-rs/blob/main/CHANGELOG.md) reports a third-party audit of `ts_tunnel` cryptography, fixes for security-relevant findings, and removal of the old experimental environment-variable requirement. That is a scoped audit claim, not proof that the entire library or an embedding application has been audited. The April 2026 launch post's DERP-only and pre-audit warnings are historical; they should not be repeated as current facts. The current README still calls direct connectivity incomplete and warns about compatibility. [Original preview announcement](https://tailscale.com/blog/tailscale-rs-rust-tsnet-library-preview).

Go [tsnet](https://tailscale.com/docs/features/tsnet) supplies an embedded tailnet node and has a longer development history, but embedding it in a Rust application raises a separate packaging, integration, cross-platform, update and lifecycle question. Tailscale describes its `tsnet.Server` as holding that node's state and providing its own tailnet identity. That differs operationally from using an already installed daemon: the application must manage enrollment and sensitive node state. [tsnet server reference](https://tailscale.com/docs/reference/tsnet-server-api), [secure node state](https://tailscale.com/docs/features/secure-node-state-storage). Do not assume Go and Rust feature, performance, or API parity.

## Failure and access boundaries

- A coordination-server outage is different from a local daemon outage. Tailscale says existing devices can keep communicating with locally cached keys and firewall rules, subject to key expiry and working peer/relay connectivity. During that outage new users or devices, policy updates, key refresh and revocation cannot be delivered. This is not a guarantee that a new, previously undiscovered peer, relay path, or connection survives every outage. [Coordination outage](https://tailscale.com/docs/reference/coordination-server-down).
- When an updated Tailscale SSH policy reaches the host, the vendor says revocation stops established Tailscale SSH connections. During a coordination outage, updated rules and key revocation cannot propagate. Do not generalize the SSH termination claim to arbitrary TCP application sessions, local processes, or alternate SSH routes; other access methods must be revoked independently. [Tailscale SSH](https://tailscale.com/docs/features/tailscale-ssh), [coordination outage](https://tailscale.com/docs/reference/coordination-server-down).
- Tailscale documents that restarting `tailscaled` terminates existing Tailscale SSH sessions. It does not by itself promise survival of the remote child process. A remote multiplexer or other session owner may keep workloads alive depending on its lifecycle and the workload, which must be tested. An embedded node in the terminal process creates an additional common failure domain: terminating that process also ends the embedded networking instance. [Tailscale SSH](https://tailscale.com/docs/features/tailscale-ssh), [tsnet server reference](https://tailscale.com/docs/reference/tsnet-server-api).
- Device key expiry can interrupt access. Avoid promising unattended availability without an explicit enrollment, key-expiry, rotation, revocation and recovery plan. Disabling expiry is an administrator's security tradeoff, not a default Ultty should silently change. [Key expiry](https://tailscale.com/docs/features/access-control/key-expiry).
- Tailscale SSH requires both network and SSH rules and enabled server support. It uses port 22 on the tailnet address and its server-side platform list is narrower than ordinary SSH. Its authentication and per-OS-user trust considerations are different from OpenSSH, especially on multi-user client hosts. [Tailscale SSH](https://tailscale.com/docs/features/tailscale-ssh).

## Performance and verification

Direct UDP usually has lower latency and higher throughput. Connections can begin through DERP, upgrade to direct, later fall back, or use an available peer relay; NAT and blocked UDP affect the route. Tailscale states DERP adds a hop and rate/throughput constraints. No vendor statement gives a universal latency guarantee or predicts Ultty rendering latency. [Connection types](https://tailscale.com/docs/reference/connection-types), [performance troubleshooting](https://tailscale.com/docs/reference/troubleshooting/poor-performance-tailnet).

Before adopting even an optional integration, compare the existing SSH path and any candidate with the same terminal output, both local and remote. Record path type and transitions, machine/build, tailnet policy, RTT, typing-to-display distribution, bulk-output throughput, CPU/memory, slow-reader behavior and reconnect outcomes. Exercise direct, forced DERP where feasible, loss, daemon restart, control outage, expired keys and actual policy revocation. Explicitly separate transport reconnection from process survival. Do not run a cloud or networking setup based on this memo alone.
